# Virus Scan Queue Contract

**Feature**: [spec.md](../spec.md)  
**Plan**: [plan.md](../plan.md)

## Purpose

Define the asynchronous handoff from the ContosoDashboard application to an Azure Function that scans an uploaded file. The same logical contract is used by the offline local background adapter so training behavior remains deterministic without Azure.

## Queue

- **Cloud transport**: Azure Queue Storage.
- **Trigger**: Azure Function Queue Storage trigger.
- **Message format**: UTF-8 JSON.
- **Payload size**: Small metadata only; never include file bytes, user secrets, access tokens, or raw user-supplied paths.
- **Visibility**: The queue is private to the application and Function identity.

## ScanWorkItem message

```json
{
  "documentId": 123,
  "scanVersion": "guid-version-token",
  "storagePath": "user-id/project-or-personal/guid.ext",
  "contentType": "application/pdf",
  "attempt": 1,
  "correlationId": "guid-correlation-id",
  "createdUtc": "2026-10-20T12:00:00Z"
}
```

### Message rules

- `documentId`, `scanVersion`, `storagePath`, and `correlationId` are required.
- `storagePath` is generated by the application and is interpreted relative to the configured storage boundary; it is not a user-selected filesystem path.
- `contentType` is informational and must not replace content inspection.
- `attempt` is bounded and is used for diagnostics; the Function must also honor the queue runtime's delivery count.
- A duplicate message with the same `documentId` and `scanVersion` must be safe to process repeatedly.

## Processing contract

1. The Function receives the message and validates its shape.
2. It obtains the file through the configured storage boundary using the generated storage identity.
3. It scans the file content with the configured malware scanner.
4. It submits a result through an authenticated application boundary.
5. The application accepts the result only when `documentId` and `scanVersion` match the current pending scan.
6. The application records the attempt and audit outcome; only a successful clean result can make the document `Available`.

The Function must not:

- Serve the file directly to users.
- Grant or revoke document access.
- Trust the original filename or content type as proof of safety.
- Overwrite a newer scan result, replacement, or deletion.
- Write arbitrary database fields from queue payload values.

## Scan result values

| Result | Document state | User access |
|---|---|---|
| `Clean` | `Available` | Browse, search, preview, download, share, and attach are allowed by authorization rules. |
| `MalwareDetected` | `Rejected` | No user access; audit event records the rejection. |
| `ScannerUnavailable` | `Pending` or `Scanning` after retry scheduling | No user access; retry while attempts remain. |
| `PermanentFailure` | `ScanFailed` | No user access; authorized operator or retry flow must create a new scan version. |
| `StaleVersion` | No state change | Record an idempotent informational outcome; never alter the current document. |

## Retry and poison-message behavior

- Transient storage, scanner, or application-boundary failures are retried by the queue-triggered Function up to the configured maximum delivery count.
- A message that exceeds the retry limit is moved to the poison/dead-letter handling path and produces an auditable `ScanFailed` outcome without making the document available.
- Reprocessing a poison message requires an authorized retry operation that creates a new `ScanVersion`; it must not reuse a stale result.
- Failures must be logged with `documentId`, `scanVersion`, `correlationId`, and a non-sensitive reason. File contents, credentials, and raw paths must not be logged.
- The offline adapter must expose equivalent retry and terminal-failure behavior for automated tests.

## Operational expectations

- Queue depth, oldest message age, retry count, poison-message count, and scan outcome counts should be observable in cloud-enabled deployments.
- The upload UI should show that the file was accepted for scanning but is not yet available; it should not claim success as a usable document until the state becomes `Available`.
- The application must tolerate delayed or duplicated results without changing authorization or exposing content.
